# 快速入门

这里的内存占用按“**一个很简单的空白 GUI 程序，启动后稳定一段时间**”给一个工程上的常见范围，不是绝对值。Windows 版本、Debug/Release、运行库、控件数量都会影响结果。

## 追求最低内存
- Win32 + WTL
- Delphi / C++Builder VCL
- MFC
- wxWidgets

这些技术空窗体通常可以控制在 10 MB 以内或略高，适合后台工具、系统托盘程序、轻量级桌面工具、老旧设备。

## 平衡开发效率和内存
- Qt Widgets
- WinForms
- Avalonia
它们空载内存在 30–60 MB 左右，但开发效率明显高于 Win32 系列。

## 现代 UI、复杂界面
如果界面需要大量动画、自定义绘制、阴影、现代化控件，内存敏感度不是第一优先级，可选：

- WPF
- WinUI 3
- Flutter Windows
- Qt Quick
这些技术空载通常在 60–150 MB 区间，但复杂界面运行时可能更高。

## 不推荐内存敏感场景
- Java Swing / JavaFX：JVM 启动和常驻内存偏高。
- Python + Qt：开发快，但发布和内存都偏重。

针对 API 测试工具这类需要**多标签页、复杂数据展示、频繁网络请求、长时间运行**的桌面应用，结合你之前对内存占用的关注，推荐以下技术栈：

## 首选：Qt Widgets（C++）

### 推荐理由

1. **多标签页内存可控**
   Qt 的 `QTabWidget` 可以轻松管理多个标签页，配合 **懒加载（按需创建）** 和 **关闭时销毁** 策略，每个标签页不会常驻内存。即使同时打开几十个请求标签，内存增长也相对平缓。
   - 空载内存约 20~50 MB，比 WPF/WinUI 低得多。
   - C++ 无 GC，对象生命周期明确，不会出现 .NET 中因事件订阅、未释放资源导致的内存泄漏累积。
2. **高性能数据展示**
   API 响应体可能非常大（几 MB 的 JSON/XML），Qt 提供了专门的控件：
   - `QPlainTextEdit`：针对大文本优化，支持语法高亮（可集成 QScintilla 或自绘），滚动流畅。
   - `QTreeView` + 自定义 Model：**虚拟化** 展示 JSON/XML 树，只渲染可见行，百万级节点也不会卡顿。
   - `QTableView`：展示响应头、参数表格，同样支持虚拟化。
3. **强大的网络与异步支持**
   Qt Network 模块提供 `QNetworkAccessManager`，支持 HTTP/HTTPS、异步请求、并发管理、SSL。配合信号槽机制，响应数据到达后自动更新 UI，不会阻塞主线程。
4. **成熟稳定的生态**
   Qt 本身就用 C++ 开发了大量复杂桌面工具（如 Qt Creator、Wireshark、VirtualBox 界面），证明了其适合构建多窗口、多标签、数据密集型的专业工具。
5. **跨平台能力**
   如果未来需要 macOS / Linux 版本，Qt 是少数能做到原生体验且性能一致的方案。

### 可能缺点

- C++ 开发效率不如 C#/Java，对团队技术要求较高。
- 商业授权需付费（LGPL 可动态链接规避）。

------

## 备选：WinForms（.NET / C#）

如果团队更熟悉 .NET，且主要面向 Windows 平台，**WinForms** 是第二选择。

### 理由

- **开发效率高**：拖拽式 UI 设计，C# 语言简洁，有大量第三方控件（如 ScintillaNET 做代码编辑、Newtonsoft.Json 解析）。
- **内存占用中等**：空载约 30~60 MB，多标签页通过 `TabControl` + `UserControl` 管理，只要及时释放资源，内存可控。
- **适合中小型工具**：对于 API 测试工具，如果没有极端性能需求（如同时打开 50+ 标签且响应体超 10 MB），WinForms 完全够用。
- **可嵌入高性能组件**：RichTextBox 处理大文本较弱，但可以集成 ScintillaNET（基于原生 Scintilla 控件）或使用自绘 ListView 虚拟模式。

### 局限

- 跨平台需依赖 Mono 或 .NET 6+，体验不如 Qt 原生。
- 大数据量渲染（如百万行 JSON 树）需要手动实现虚拟化，否则容易卡顿。

## 不推荐的技术栈及原因

| 技术栈                  | 不适合的原因                                                 |
| :---------------------- | :----------------------------------------------------------- |
| **Win32 / WTL / MFC**   | 开发复杂 UI（代码编辑器、JSON 树、表格）工作量巨大，效率极低。 |
| **WPF / WinUI 3**       | 内存占用偏高（空载 60~150 MB），多标签 + 复杂模板容易导致内存膨胀；GPU 资源消耗也大。 |
| **Flutter Windows**     | 桌面端生态尚未完全成熟，网络库、系统集成、文本编辑控件等不如 Qt 完善；性能虽好但团队学习成本高。 |
| **Java Swing / JavaFX** | JVM 启动慢、常驻内存高（100 MB+），不适合需要轻量启动的测试工具。 |
| **Python + Qt**         | 开发快但解释器常驻内存 30~80 MB，且大量请求或数据处理时性能瓶颈明显。 |

------

## 总结

**API 测试工具首选 Qt Widgets**，它在内存占用、渲染性能、多标签管理和网络支持上达到了最佳平衡，尤其适合你可能同时打开几十个请求标签、查看大响应体的场景。如果团队 C++ 能力不足，且仅面向 Windows，**WinForms** 是更现实的备选方案。

## 最终选择

如果是我来做这个产品，我会选择：

> **C++23 + Qt 6 Widgets + Scintilla + libcurl + simdjson + SQLite**

理由是它特别符合 API 测试工具的几个核心要求：

**多 Tab、大文本、大 JSON、长时间运行、低内存、复杂桌面布局、跨平台。**

如果你更在意开发速度而不是极限内存，我会选择：

> **C# + WPF + AvalonEdit + HttpClient + System.Text.Json + SQLite**

两套里，我认为 **WPF 是“性价比最高”**，而 **Qt 是“最终产品上限最高”**。

如果你准备把它做成一个真正对标 Postman/Apifox 的长期项目，那么我会直接选 **Qt Widgets，而不是 Qt Quick**。
